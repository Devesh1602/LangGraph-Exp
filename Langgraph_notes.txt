LangGraph is a graph-based orchestration framework for building stateful LLM and agent applications. We define a shared state, represent individual operations as nodes, and connect those nodes using edges. Conditional edges allow dynamic routing and loops. It is particularly useful for agentic applications involving tool calling, RAG, multi-agent workflows, human-in-the-loop, retries, and persistent execution. LangChain provides many of the underlying LLM and tool components, while LangGraph manages the workflow and stateful orchestration

State

Shared information passed through graph execution.

Node

A unit of computation.

Edge

Defines transition between nodes.

Conditional Edge

Determines next node based on state/output.

START

Entry point.

END

Termination point.

Graph

Collection of nodes + edges + state definition.

Checkpoint

Persisted graph state used for recovery/resumption.

Thread

Logical execution/conversation context.

Tool

External capability available to the agent.

Human-in-the-loop

Pause execution for human decision/approval.

Reducer

Mechanism for combining updates when multiple graph paths modify the same state field.

Graph API gives explicit control over the workflow by defining nodes, edges, and state
Functional API allows us to use normal Python control flow to define the workflow, making it simpler when an explicit graph structure isn't necessary

| Feature           | Graph API            | Functional API           |
| ----------------- | -------------------- | ------------------------ |
| Workflow style    | Explicit graph       | Python control flow      |
| Nodes/edges       | Explicitly defined   | Implicit                 |
| State             | Explicit             | Managed through workflow |
| Complex branching | Excellent            | Good                     |
| Loops             | Explicit graph edges | Normal Python loops      |
| Multi-agent       | Excellent            | Possible                 |
| Visualization     | Easier               | Less explicit            |
| Best for          | Complex workflows    | Simple/linear workflows  |


The Graph API explicitly defines the workflow using state, nodes, and edges, so it's ideal for complex agentic workflows with branching, loops, and multiple agents. The Functional API allows us to define the workflow using normal Python control flow such as function calls, if-else, and loops. So I would use Graph API when I need explicit graph-level control and Functional API when the workflow is simpler and Python control flow is sufficient

In LangGraph, reducers are functions that define how state updates from multiple nodes are merged, preventing data loss by controlling whether values are overwritten, appended, or custom-aggregated.
These functions are critical for parallel execution and multi-agent systems, ensuring that concurrent writes to the same state key are combined deterministically rather than randomly.

ReAct Agent Architecture:
Why it came:
raw LLM on its own is fundamentally limited: it can think, but it cannot act; it can generate reasoning, but it lacks persistent state and structured control over execution.
This gap is where AI agents emerge—and among agentic patterns, ReAct (Reason + Act) has become one of the most influential.
Reason → Act → Observe → Repeat
Instead of forcing the LLM to answer everything directly, we allow it to:

1. Reason about what it knows and what it needs 
2. Act by invoking tools (search, APIs, databases, calculators) 
3. Observe the result of those actions 
4. Refine its reasoning based on new information
