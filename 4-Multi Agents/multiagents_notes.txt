# Multi-Agent AI with LangGraph — Interview Notes

## 1. What this notebook demonstrates

This notebook shows **three levels of multi-agent architecture**:

1. **Simple Multi-Agent** → Researcher → Writer
2. **Supervisor Multi-Agent** → Supervisor dynamically routes Researcher → Analyst → Writer
3. **Hierarchical Multi-Agent** → Team leaders manage specialized agents

The important idea is:

> Instead of one agent doing everything, multiple specialized agents collaborate through shared state.

---

# PART 1 — Simple Multi-Agent

## 2. Define State

```python
class AgentState(MessagesState):
    next_agent: str
```

`AgentState` contains:

* `messages` → inherited from `MessagesState`
* `next_agent` → identifies which agent should execute next.

**Remember:**

> **State = shared information between agents.**

## 3. Create Tools

### Web Search

```python
@tool
def search_web(query: str) -> str:
    search = TavilySearchResults(max_results=3)
    results = search.invoke(query)
    return str(results)
```

The Researcher can use Tavily to search the web.

### Summary Tool

```python
@tool
def write_summary(content: str) -> str:
    summary = f"Summary of findings:\n\n{content[:500]}..."
    return summary
```

Creates a simple summary from supplied content.

**Important:** In the actual simple workflow below, `write_summary` is defined but is not connected to the graph's active routing logic.

# 6. Writer Agent

```python
def writer_agent(state: AgentState):
```

The Writer receives the conversation and asks the LLM to create a concise summary.

It returns:

```python

```

### Interview point

This is a **multi-agent workflow**, but the routing is predetermined.

The Researcher always goes to the Writer.

# 7. Build Simple Graph

```python
workflow = StateGraph(MessagesState)

workflow.add_node("researcher", researcher_agent)
workflow.add_node("writer", writer_agent)

workflow.set_entry_point("researcher")

workflow.add_edge("researcher", "writer")
workflow.add_edge("writer", END)

final_workflow = workflow.compile()
```

The graph is:

```text
START → Researcher → Writer → END
```

# PART 2 — Supervisor Multi-Agent

This is the more important architecture for interviews.

## 8. Define Supervisor State

```python
class SupervisorState(MessagesState):
    next_agent: str = ""
    research_data: str = ""
    analysis: str = ""
    final_report: str = ""
    task_complete: bool = False
    current_task: str = ""
```

The shared state now contains specialized fields:

* `research_data` → Researcher's output.
* `analysis` → Analyst's output.
* `final_report` → Writer's final report.
* `current_task` → original task.
* `next_agent` → next agent to execute.
* `task_complete` → whether work is finished.

**Interview point:**

> The agents communicate through shared graph state rather than directly calling each other.

---

# 9. Supervisor

```python
def supervisor_agent(state: SupervisorState):
```

The Supervisor decides **which agent should work next**.

Available agents:

```text
Researcher
Analyst
Writer
```

The supervisor prompt checks:

```text
Has research?
Has analysis?
Has report?
```

Then asks the LLM to choose:

```text
researcher
analyst
writer
DONE
```

---

# 10. Supervisor Decision Logic

```python
if "done" in decision_text or has_report:
    next_agent = "end"

elif "researcher" in decision_text or not has_research:
    next_agent = "researcher"

elif "analyst" in decision_text or (has_research and not has_analysis):
    next_agent = "analyst"

elif "writer" in decision_text or (has_analysis and not has_report):
    next_agent = "writer"
```

This combines the LLM's decision with state-based checks.

### Basic workflow

```text
             Supervisor
            /     |     \
           ↓      ↓      ↓
     Researcher Analyst Writer
           ↓      ↓      ↓
             Supervisor
                  ↓
                 END
```

The Supervisor acts as the **orchestrator/router**.

---

* `analysis`

The report contains:

# 14. Router Function

```python
def router(state: SupervisorState):
```

The router looks at:

```python
state["next_agent"]
```

and decides where the graph should go.

Possible destinations:

```text
supervisor
researcher
analyst
writer
END
```

This separates **decision-making from graph routing**.

### Important distinction

**Supervisor**

→ decides what should happen next.

**Router**

→ translates that decision into a graph edge.

---

# 15. Build Supervisor Graph

```python
workflow = StateGraph(SupervisorState)
```

Add nodes:

```python
workflow.add_node("supervisor", supervisor_agent)
workflow.add_node("researcher", researcher_agent)
workflow.add_node("analyst", analyst_agent)
workflow.add_node("writer", writer_agent)
```

Set entry:

```python
workflow.set_entry_point("supervisor")
```

Then conditional routing is added for every node.

# Simple vs Supervisor Multi-Agent

| Simple Multi-Agent         | Supervisor Multi-Agent     |
| -------------------------- | -------------------------- |
| Fixed routing              | Dynamic routing            |
| Researcher → Writer        | Supervisor decides         |
| Less flexible              | More flexible              |
| Simple workflow            | Stateful orchestration     |
| Good for predictable tasks | Good for complex workflows |

### Interview answer

> "In a simple multi-agent workflow, agents can follow a predefined sequence. In a supervisor architecture, a dedicated supervisor dynamically decides which specialized agent should execute next based on the current state."

# Multi-Agent vs Single Agent

### Single Agent

```text
User
 ↓
One Agent
 ↓
Tools
 ↓
Answer
```

### Multi-Agent

```text
             Supervisor
            /     |     \
           ↓      ↓      ↓
     Researcher Analyst Writer
```

Each agent has a **specific responsibility**.

### Why use multiple agents?

* Separation of responsibilities
* Easier specialization
* Better organization of complex workflows
* Independent prompts/logic for different tasks
* More controllable orchestration

# What to Remember for Interview

## Core Components

### `MessagesState`

→ Stores conversation messages.

### `SupervisorState`

→ Shared state containing messages + task-specific outputs.

### Researcher

→ Gathers information.

### Analyst

→ Analyzes research.

### Writer

→ Creates final report.

### Supervisor

→ Decides which agent works next.

### Router

→ Routes graph execution according to `next_agent`.

---

# Most Important Interview Concept

### Supervisor vs Router

**Supervisor = Decision Maker**

> "Who should work next?"

**Router = Graph Controller**

> "Send execution to that node."

# Interview-Ready Explanation

> "This notebook demonstrates multi-agent orchestration using LangGraph. In the simple architecture, a Researcher performs research and the Writer creates a summary through a fixed Researcher-to-Writer workflow. The supervisor architecture is more flexible: a Supervisor LLM examines the shared state and decides whether the Researcher, Analyst, or Writer should execute next. Each agent writes its results into the shared state, and control returns to the Supervisor until the task is complete. This creates a stateful, dynamically routed multi-agent workflow."

## One-Line Memory Trick

**`Supervisor → Research → Analyze → Write → Supervisor → END`**

### The 6 things to memorize

```text
State       → Shared information
Agent       → Specialized worker
Supervisor  → Decides next worker
Router      → Controls graph path
LangGraph   → Orchestrates workflow
LLM         → Provides reasoning/generation
```

**One code-quality point to remember:** In the simple architecture, `execute_tools()` is defined but never added as a graph node, so it is not actually part of `final_workflow`. Also, the simple graph is created with `StateGraph(MessagesState)` even though the custom `AgentState` is defined; the custom `next_agent` field therefore isn't represented in that graph's declared state.
